# گزارش ممیزی داده و گردش تأیید Boya UI

**تاریخ گزارش:** ۲ نوامبر ۲۰۲۶  
**مبنای گزارش:** شش نتیجهٔ بازبینی کد ارائه‌شده (DB، API، پنل ادمین، پنل سالن، کاتالوگ مشتری، آزمون و انتشار).  
**دامنه:** ردیابی ذخیره‌سازی و نمایش تأیید سالن، متخصص و خدمت از پنل‌های مدیریتی تا کاتالوگ مشتری؛ همراه با یافته‌های امنیتی و عملیاتی مؤثر بر این جریان.

## نتیجهٔ اجرایی

**پاسخ کوتاه: خیر، برای هر سه موجودیت نمی‌توان گفت تأییدهای پنل ادمین/ارائه‌دهنده در یک پایگاه‌دادهٔ canonical پایدار می‌شوند و سپس به‌طور قابل اتکا به فهرست مشتریان می‌رسند.** طرح‌واره PostgreSQL/Drizzle برای سالن و متخصص فیلدهای canonical تأیید دارد و PATCH سالن در حالت موفق به DB می‌نویسد؛ اما کد مسیر عمومی سالن را بدون فیلتر تأیید می‌خواند، و UI مشتری نیز آن را فیلتر نمی‌کند. تغییرات متخصص در پنل مدیریت بررسی‌شده فقط در Zustand محلی‌اند و CRUD سروری متناظر پیدا نشد. برای خدمت، وضعیت تأیید مستقلی در schema دیده نمی‌شود؛ افزودن خدمت در پنل سالن به PATCH سالن فرستاده می‌شود، ولی اعتبارسنجی API فیلد `services` را نمی‌پذیرد و جدول `services` جداست، پس ذخیرهٔ آن اثبات نمی‌شود.

| موجودیت | وضعیت canonical DB | نتیجهٔ تأیید/مدیریت | انتقال به فهرست مشتری |
|---|---|---|---|
| سالن | `salons.isApproved` در schema و migration وجود دارد؛ PATCH سالن، از جمله `isApproved`، مسیر DB دارد. | تأیید در پنل ادمین به API می‌رود؛ ولی `updateSalon` خطا را می‌بلعد. POST سالن در backend آن را مستقیم `isApproved:true` می‌سازد. وضعیت‌های دیگر مورد استفاده UI در schema اعتبارسنجی‌شده نیستند. | تضمین ندارد: GET عمومی همه سالن‌ها را می‌خواند و UI مشتری شرط تأیید/فعال‌بودن ندارد؛ بنابراین pending/rejected ممکن است نمایش داده شود. |
| متخصص | `specialists.isVerified` در schema و مقدار پیش‌فرض `false` وجود دارد. | پنل AdminSpecialistsView ساخت/ویرایش/حذف/تأیید را فقط در store محلی انجام می‌دهد؛ CRUD API متخصص در فایل backend بررسی‌شده یافت نشد. یک مسیر portfolio پرخطر نیز در backend اجازهٔ انتساب شناسهٔ متخصص را دارد. | تغییر محلی پایدار نیست و از کاتالوگ DB-محور مشتری قابل اتکا نیست. نمایش متخصصان از رابطهٔ DB سالن می‌آید. |
| خدمت | جدول canonical `services` دارد، اما فیلد تأیید/فعال/نمایان در schema دیده نمی‌شود. | پنل سالن خدمت را در `services` محلی می‌افزاید و `updateSalon` را با آرایهٔ خدمات صدا می‌زند؛ Zod آن را حذف می‌کند و PATCH فقط جدول سالن را به‌روزرسانی می‌کند. پنل ادمین نیز CRUD قابل‌ردیابی خدمت ندارد. | خدمت تازه از مسیرهای بررسی‌شده به DB و در نتیجه به کاتالوگ مشتری نمی‌رسد؛ GET مشتری خدمات را از رابطه‌های DB دریافت می‌کند. |

## دامنه و روش‌شناسی

این گزارش ترکیبی از شش بازبینی ایستا است: طرح‌واره و persistence، API و احراز هویت، گردش تأیید ادمین، پنل salon-admin، کاتالوگ و cache مشتری، و آزمون/آمادگی انتشار. مسیرهای داده از مؤلفه‌های UI، store و query، routeهای Express، اعتبارسنجی Zod، Drizzle schema/migration و آزمون‌های موجود دنبال شده‌اند. یافته‌ها فقط به شواهد و مسیر/شماره‌خط‌های گزارش‌شده متکی‌اند. نبود endpoint یا رفتار در فایل‌های بررسی‌شده به معنی نبود قطعی آن در سرویس خارجی یا محیط خارج از checkout نیست.

## نمودار متنی جریان داده

```text
پنل AdminApprovalsView
  └─ updateSalon → Zustand dataStore
       └─ PATCH /api/salons/:id → salonUpdateSchema → UPDATE salons
            └─ GET /api/salons → relationهای services و specialists از DB
                 └─ useSalons / React Query ['salons'] → HomeScreen و SalonsScreen
                      └─ فیلتر مکان/جست‌وجو/... → SalonCard و مسیر رزرو

پنل AdminSpecialistsView ── setSalons محلی ──X── PostgreSQL
پنل salon-admin افزودن service ── updateSalon(services) → PATCH
   └─ Zod فیلد ناشناخته services را حذف می‌کند ──X── جدول services
پنل salon-admin متخصصان ── خواندن specialist از salon object؛ mutation سروری دیده نشد

محدودیت انتشار مشتری در کد بررسی‌شده:
GET /api/salons: بدون شرط isApproved؛ صفحات مشتری نیز بدون شرط isApproved/status
```

## یافته‌ها به ترتیب شدت

درجه‌بندی شدت همان شدت گزارش‌شده در بازبینی‌هاست. یافته‌های هم‌پوشان ادغام شده‌اند، بدون حذف مسیرهای شواهد.

### بحرانی

#### ۱. کنترل تأیید سالن قابل دور زدن و فهرست عمومی بدون پالایش
**شواهد:** `server.ts:340-352`، GET عمومی سالن بدون احراز هویت و شرط `isApproved` همهٔ سالن‌ها را می‌خواند؛ `server.ts:383-397` PATCH سالن را برای `super_admin` و `salon_admin` می‌پذیرد؛ `src/lib/validation.ts:38-52` فیلد `isApproved` را در schema تغییر سالن می‌پذیرد؛ `src/db/schema.ts:62` پیش‌فرض را false می‌گذارد. تکمیل شواهد کاتالوگ: `src/features/salons/components/SalonsScreen.tsx:77-92` فیلتر تأیید ندارد؛ `src/features/home/components/HomeScreen.tsx:58-81` نیز همین‌طور است؛ `src/shared/components/ui/SalonCard.tsx:133-137` تأیید را فقط نشان می‌دهد.

**اثر:** سالن تأییدنشده/ردشده می‌تواند از endpoint عمومی بازگردد و در فهرست مشتری دیده شود. افزون بر آن، مدیر سالن مجاز به تغییر `isApproved` در PATCH خود سالن است؛ در نتیجه مرز تصمیم تأیید فقط به super-admin محدود نیست.

**اصلاح:** `isApproved` را از PATCH عمومی/مدیر سالن خارج کنید؛ endpoint تصمیم‌گیری مجزا و super-admin-only بسازید؛ GET عمومی را در خود DB به `isApproved=true` و وضعیت انتشار معتبر محدود کنید و DTO عمومی حداقلی برگردانید. همان شرط را دفاعی در UI و مسیر رزرو هم اعمال کنید.

#### ۲. مسیر portfolio امکان دست‌کاری متخصص دیگر و ساخت متخصص تأییدشده دارد
**شواهد:** `server.ts:280` مسیر `POST /api/specialists/portfolio` فقط `requireAuth` دارد؛ `server.ts:285-301` در نبود متخصص کاربر، `specialistId` ارسالی را بدون مالکیت‌سنجی می‌گیرد و در حالت خاص متخصص با `isVerified=true` و سالن پیش‌فرض ۱ می‌سازد؛ `server.ts:305-311` portfolio را با شناسهٔ انتخابی درج می‌کند.

**اثر:** کاربر واردشده می‌تواند محتوای portfolio متخصص دیگر را تغییر دهد و ممکن است پروفایل متخصص تأییدشده بسازد.

**اصلاح:** شناسه را صرفاً از هویت احرازشده و رکورد مرتبط استخراج کنید؛ نقش/مالکیت/سالن را در سرور کنترل کنید؛ تأیید فقط از workflow مدیریتی انجام شود و ورودی‌ها با Zod محدود شوند.

### بالا

#### ۳. خودارتقایی نقش و ساخت کاربر ادمینی در API
**شواهد:** `server.ts:525-544` PATCH کاربر، برای مدیر سالن روی حساب خودش فیلدهای role/status/salonId را حذف نمی‌کند؛ `src/lib/validation.ts:27-36` این فیلدها را می‌پذیرد. در ساخت کاربر، `server.ts:467-483` اجازهٔ `salon_admin` را می‌دهد و `salonId` ورودی را می‌نویسد؛ `src/lib/validation.ts:53-59` نقش‌های `salon_admin` و `super_admin` را می‌پذیرد.

**اثر:** مدیر سالن می‌تواند نقش و دامنهٔ حساب خود را تغییر دهد و طبق منطق گزارش‌شده امکان ارتقای خطرناک وجود دارد؛ همچنین می‌تواند حساب‌های پرقدرت یا انتساب‌های خارج از سالن خود بسازد.

**اصلاح:** تغییر role/status/salonId را فقط به super-admin محدود کنید و target را نیز محدود سازید؛ ساخت super-admin را از endpoint عمومی حذف کنید؛ salonId را از هویت مجاز سروری استخراج کنید، نه از payload. فیلتر tenant را در query DB اجرا کنید.

#### ۴. CRUD متخصص در UI محلی است؛ CRUD خدمت در API/پنل قابل ردیابی نیست
**شواهد متخصص:** `src/features/admin/components/AdminSpecialistsView.tsx:84-115` و `117-179` تغییرات را با `setSalons` انجام می‌دهد؛ `src/shared/stores/dataStore.ts:142` آن را صرفاً state می‌داند؛ `src/db/schema.ts:84-95` متخصص جدول جدا دارد؛ `server.ts:279-336` عملیات متخصص را به portfolio محدود می‌کند و CRUD متخصص ندارد.

**شواهد خدمت:** `src/features/salon-admin/components/SalonAdminDashboard.tsx:347-373` افزودن خدمت را با `updateSalon` انجام می‌دهد؛ `src/shared/stores/dataStore.ts:161-169` PATCH می‌زند؛ `src/lib/validation.ts:38-52` فیلد `services` را نمی‌پذیرد؛ `server.ts:383-398` فقط patch معتبر سالن را ذخیره می‌کند؛ `src/db/schema.ts:71-82` خدمات جدول جدا دارند. `src/features/admin/components/AdminTenantsView.tsx:557-561` خدمات انتخاب‌شده را فقط به‌صورت شمارنده نمایش می‌دهد و CRUD متناظر ندارد.

**اثر:** ساخت/ویرایش/حذف/تأیید متخصص و افزودن خدمت از مسیرهای یادشده در DB canonical پایدار نمی‌شود؛ reload یا دریافت مجدد داده آن را از میان می‌برد و مشتری تغییر را نمی‌بیند.

**اصلاح:** endpointهای CRUD مستقل برای services و specialists بسازید؛ نقش و مالکیت سالن را سمت سرور کنترل کنید؛ برای تأیید متخصص فقط مدیر مجاز تصمیم بگیرد؛ از شناسه‌های DB استفاده کنید و UI را فقط پس از پاسخ موفق با پاسخ canonical به‌روز کنید.

#### ۵. رزرو هم‌زمان و وضعیت تأیید در لایهٔ رزرو کنترل نمی‌شود
**شواهد:** `src/db/bookings.ts:26-60` وجود و تعلق سالن/خدمت/متخصص را بررسی می‌کند اما `isApproved`/`isVerified` را نمی‌خواند؛ `src/db/bookings.ts:65-79` درج جداگانه انجام می‌شود. `server.ts:563-574` بررسی slot قبل از insert است؛ `src/db/schema.ts:113-116` قید یکتا همهٔ statusها را شامل می‌کند؛ `server.ts:570` رزرو لغوشده را آزاد می‌داند، ولی قید DB همچنان slot را اشغال می‌کند.

**اثر:** امکان رزرو برای سالن/متخصص تأییدنشده و ناسازگاری در رقابت هم‌زمان یا رزرو مجدد پس از لغو. کلیدهای خارجی مستقل نیز تطابق متقابل سالن/خدمت/متخصص را تضمین نمی‌کنند.

**اصلاح:** وضعیت انتشار و تأیید را هنگام رزرو دوباره کنترل کنید؛ check و insert را اتمیک کنید؛ قید را فقط برای رزروهای مسدودکننده طراحی کنید؛ تاریخ/زمان و تعلق line/mobile را اعتبارسنجی و در صورت امکان با قیود DB پشتیبانی کنید.

### متوسط

#### ۶. تغییرات approval ممکن است موفقیت کاذب نشان دهند؛ وضعیت/سند درخواست بازبینی پایدار نیست
**شواهد:** `src/features/admin/components/AdminApprovalsView.tsx:19-33` تصمیم را با `updateSalon` می‌فرستد؛ `src/shared/stores/dataStore.ts:161-169` خطا را فقط log می‌کند. `src/features/salon-admin/components/SalonAdminDashboard.tsx:474-489` `pendingApproval` را می‌فرستد؛ `src/lib/validation.ts:38-52` آن را نمی‌پذیرد. `AdminApprovalsView.tsx:19-33` وضعیت و سند را نیز می‌فرستد، اما `src/lib/validation.ts:47-52` فقط `isApproved` را از آن‌ها می‌پذیرد. `src/db/schema.ts:49-69` برای سالن `isApproved` دارد، نه چرخهٔ status گزارش‌شده.

**اثر:** PATCH موفق می‌تواند `isApproved` را تغییر دهد، اما UI ممکن است شکست را پنهان کند؛ `pendingApproval`، statusهای active/suspended و سند مجوز در مسیر فعلی ذخیره‌شدنشان اثبات نشده است.

**اصلاح:** خطای mutation را propagate کنید؛ UI تنها پس از پاسخ موفق پیام موفقیت دهد؛ فیلدها و workflow را در schema/API/DB صریح و versioned کنید یا endpoint approval جدا بسازید و تغییرات را audit کنید.

#### ۷. cache کاتالوگ و fallback رفتار روشن/همگام ندارد
**شواهد:** `src/shared/api/queries.ts:5-19` در خطا یا پاسخ خالی به Zustand برمی‌گردد؛ `src/shared/api/queryClient.tsx:4-10` stale time پنج دقیقه است؛ `src/shared/stores/dataStore.ts:280-286` salons در persist ثبت نمی‌شود. پنل salon-admin تغییر را بدون invalidation عمومی انجام می‌دهد؛ invalidationهای مشخص در `SalonAdminDashboard.tsx:567-569,600` به همهٔ مسیرها مربوط نیستند.

**اثر:** مشتری ممکن است دادهٔ قدیمی ببیند؛ پاسخ خالی API از خطا متمایز نشده و fallback معمولاً state خالی است؛ تغییر محلی ماندگار یا قابل مشاهده در تب دیگر نیست.

**اصلاح:** رفتار offline/error/empty را تفکیک کنید؛ mutationهای موفق را به پاسخ DB متصل کنید و queryهای `['salons']` و جزئیات مرتبط را invalidate یا با پاسخ سرور به‌روزرسانی کنید.

#### ۸. ملاحظات امنیت و یکپارچگی داده در API و DB
**شواهد:** `src/db/schema.ts:43-44` برای `users.salonId` FK ندارد؛ `server.ts:340-374` پاسخ عمومی را از relationها می‌سازد؛ `server.ts:467-487` پاسخ ساخت کاربر را بدون redact برمی‌گرداند؛ `src/lib/jwt.ts:3-11,13` در غیرتولیدی secret ثابت fallback و توکن ۳۰روزه دارد؛ `server.ts:63-64,167-177` OTP/rate limit حافظه‌ای است و کد توسعه در log می‌شود. `src/db/schema.ts:103-116` تاریخ/زمان متنی و unique اسلات بدون توجه به status دارد.

**اثر:** دادهٔ حساس ممکن است بیش از نیاز در پاسخ باشد؛ پیکربندی ناامن یا چند replica ریسک ایجاد می‌کند؛ دادهٔ یتیم و قید رزرو ناسازگار محتمل است.

**اصلاح:** پاسخ‌ها را با DTO allowlist محدود کنید؛ secret تصادفی و کوتاه‌عمرسازی/rotation توکن را الزام کنید؛ OTP و محدودسازی را در storage مشترک اتمیک قرار دهید؛ FK و مدل زمانی/اسلات را بازطراحی کنید.

### کم

#### ۹. قرارداد API client محلی و proxy خارجی متفاوت است
**شواهد:** `src/shared/api/boyaApi.ts:9,66-99` به `/api/v1/...` می‌زند؛ `server.ts:626` `/api/v1` را به `https://boya.bcshopir.ir/api/v1` proxy می‌کند؛ API محلی سالن در `server.ts:340-381` زیر `/api/salons` است.

**اثر:** نتیجهٔ آزمون UI علیه backend محلی را نمی‌توان به backend خارجی تعمیم داد؛ منبع دادهٔ کلاینت ممکن است سرویس دیگری باشد.

**اصلاح:** قرارداد و منبع API را صریح و محیطی کنید؛ routeهای محلی/خارجی را جدا نگه دارید و آزمون قراردادی برای هر backend داشته باشید.

## نقاط قوت مشاهده‌شده

- schema روابط روشن برای `salons`، `services`، `specialists` و `bookings` دارد؛ رزرو، شناسه‌های مستقل و FKهای اصلی را ثبت می‌کند (`src/db/schema.ts:62-102`).
- `isApproved` سالن و `isVerified` متخصص در DB مقدار پیش‌فرض false دارند (`src/db/schema.ts:62,91-92`).
- مسیر رزرو قیمت خدمت را از رکورد DB می‌خواند، نه اینکه به قیمت ورودی کلاینت اعتماد کند (`src/db/bookings.ts:62-79`).
- routeهای سالن برای PATCH احراز هویت و کنترل نقش دارند و ایجاد/حذف سالن به super-admin محدود شده‌اند (`server.ts:383-415,439-440`)، هرچند مجوز تغییر فیلد approval نیازمند سخت‌گیری است.
- middleware نقش را از DB دوباره می‌خواند؛ نقش snapshot توکن مبنای authorization گزارش نشده است (`src/middleware/auth.ts:35-50`).
- در UI مسیر `/admin` به super-admin محدود شده است (`src/shared/router/router.tsx:189-195`)، اما کنترل UI جایگزین کنترل API نیست.
- آزمون E2E فعلی دست‌کم مسیر بازکردن modal رزرو و نیاز ورود را پوشش می‌دهد (`e2e/booking.spec.ts:3-24`).

1. GET عمومی را در query DB به سالن‌های منتشرشده/تأییدشده محدود کنید؛ PATCH ادمین سالن را از تغییر approval محروم کنید و endpoint تصمیم‌گیری super-admin-only ایجاد کنید.
2. مسیر portfolio را به متخصص احرازشده محدود و ساخت متخصص/تأیید ضمنی را حذف کنید.
3. PATCH نقش و ساخت کاربران را سخت‌گیرانه ببندید؛ self-role-change و ساخت super-admin از مسیر salon-admin را مسدود کنید.
4. رزرو را از نظر approval/verification و تعلق سرویس/متخصص کنترل کنید.

### فاز یک — canonical CRUD و قابلیت مشاهده
1. CRUD واقعی خدمت و متخصص را روی جدول‌های canonical پیاده کنید؛ اعتبارسنجی Zod، tenant scope و مجوز نقش را در API برقرار کنید.
2. UI پنل‌ها را از تغییر مستقیم `setSalons` به mutationهای API منتقل کنید؛ شناسهٔ DB و پاسخ canonical را نگه دارید.
3. برای خدمات و متخصصان چرخهٔ حیات/visibility/approval را تصمیم‌گیری و در DB و API مدل کنید.
4. خطاها را از store به UI برگردانید؛ موفقیت را فقط پس از write موفق اعلام کنید و query cache را invalidate کنید.

### فاز دو — یکپارچگی داده و عملیات
1. رزرو را اتمیک کنید و مدل تاریخ، زمان، لغو و هم‌پوشانی خدمت را اصلاح کنید؛ قیود ترکیبی مناسب را بررسی کنید.
2. FK `users.salonId` و سیاست snapshot تاریخی خدمت/قیمت را تعیین و migration امن اضافه کنید.
3. تنظیمات DB را fail-fast و یکسان کنید؛ seed را idempotent، قابل مشاهده در شکست و تفکیک‌شده برحسب محیط سازید.
4. دستور migration release را تعریف و در CI/staging روی DB خالی و موجود اجرا کنید؛ مستندات `npm start` را با اسکریپت واقعی هماهنگ کنید.
5. JWT و OTP را با secret/storage مشترک امن کنید؛ پاسخ‌های عمومی و ادمینی را به DTOهای حداقلی محدود کنید.

## آزمون‌های سرتاسری پیشنهادی

1. **تأیید سالن تا مشتری:** با DB تستی و دادهٔ ایزوله، سالن pending بسازید؛ GET عمومی آن را نبیند؛ با super-admin تأیید کنید؛ مستقیماً DB و پاسخ API را پس از reload بررسی کنید؛ با نشست مشتری مستقل آن را در فهرست ببینید.
2. **رد/لغو انتشار:** سالن ردشده یا suspended باید از GET عمومی، صفحهٔ خانه، جست‌وجو و مسیر رزرو حذف/مسدود باشد؛ با URL مستقیم نیز قابل رزرو نباشد.
3. **مجوز تأیید:** salon_admin نتواند `isApproved` یا نقش خود را تغییر دهد؛ super-admin مجاز باشد؛ درخواست نامعتبر پاسخ خطای قابل نمایش بدهد و DB را تغییر ندهد.
4. **متخصص canonical:** create/update/delete/verify متخصص از UI به API و DB برود؛ پس از refresh و نشست مشتری دیگر همان نتیجهٔ DB دیده شود؛ کاربر دیگر نتواند portfolio یا متخصص را دست‌کاری کند.
5. **خدمت canonical:** افزودن/ویرایش/حذف خدمت از پنل سالن در جدول `services` ثبت شود؛ salonId و مجوز کنترل شوند؛ مشتری پس از invalidation/reload خدمت را ببیند و خدمت غیرفعال را رزرو نکند.
6. **شکست شبکه:** PATCH approval و CRUD را عمداً fail کنید؛ UI موفقیت کاذب ندهد، state/cache به‌روزرسانی نشود و پیام retry/error نمایش دهد.
7. **رزرو و قیود:** سالن/متخصص تأییدنشده، service متعلق به سالن دیگر، ترکیب نامعتبر line/mobile و slot لغوشده/هم‌زمان را پوشش دهید؛ DB و API نتیجهٔ سازگار بدهند.
8. **Migration و seed:** migration روی DB خالی و نسخهٔ قبلی اجرا شود؛ شکست migration مانع انتشار شود؛ seed دوباره‌اجراپذیر و خطاهای نیمه‌کاره قابل تشخیص باشند.

## محدودیت‌ها و موارد نیازمند راستی‌آزمایی

- **هیچ اعتبارنامهٔ DB زنده‌ای در اختیار نبود؛ بنابراین هیچ بررسی runtime روی پایگاه‌دادهٔ زنده انجام نشده است.** وجود schema/migration در مخزن، اثبات اعمال آن روی محیط واقعی نیست.
- endpoint خارجی `/api/v1` و هر backend خارج از checkout بررسی‌شده نبود؛ ممکن است آنجا CRUD یا فیلترهای دیگری پیاده شده باشند.
- اجرای migration خارج از repository یا deployment، proxy/middleware بیرونی، و دادهٔ موجود در production مستقلاً راستی‌آزمایی نشده‌اند.
- نتیجه دربارهٔ فیلتر عمومی بر کد `server.ts` و UI مشتریِ ارائه‌شده است؛ تنظیمات بیرونی نامشهود می‌تواند رفتار محیط مستقر را تغییر دهد.
- وضعیت‌های `active/pending/suspended` و ذخیرهٔ سند مجوز در schema/validation مشاهده‌شده پشتیبانی کامل ندارند؛ رفتار واقعی DB خارج از شواهد کد قطعی نیست.
- هیچ ادعایی مبنی بر اجرای واقعی مسیر تأیید در production یا مشاهدهٔ ردیف‌های DB نشده است؛ نتیجه‌ها استنتاج از شواهد کد ارائه‌شده‌اند.
